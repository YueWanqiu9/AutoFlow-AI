# AutoFlow AI

**智能服务工单与运营自动化系统 · V2.0 面试演示版**

## 项目简介

将非结构化客户需求，通过 AI 解析、信息补全、资源匹配和运营决策，转化为可执行、可追踪的服务流程。

AutoFlow AI 面向服务行业的客服与运营管理。AI 的输出进入工单、审核、派单和服务跟踪，最终成为可追溯的业务记录，而非止于一次聊天回复。

打开首页，点击 **“一键运行完整演示”**，无需 API Key 即可展示十步闭环。演示首页用于讲解，运营工作台保留逐项操作能力。

## 业务场景

客户说：“我母亲82岁，行动不便，希望明天下午两点安排护理员上门照护，地址红塔区山水佳园。”

客服需要提取需求，补齐姓名和电话，运营需要确定优先级、核对处理方案与人员条件，之后追踪派单和服务进度。

| 运营痛点 | 系统如何支持 |
| --- | --- |
| 自然语言信息零散、字段遗漏 | 六字段结构化解析，发现缺失后围绕原工单补问 |
| 判断依赖个人经验 | 展示规则依据和 AI 说明，运营保留最终确认权 |
| 人员匹配需要反复核对 | 按技能、服务区域、登记状态生成可解释排序 |
| 服务过程难以追踪 | 派单状态机、时间记录、异常原因与操作事件 |
| 统计口径混淆 | 工单状态、服务进度、真实 AI 调用分开统计 |

以上案例与完整演示中的客户、联系方式、人员及服务结果均为虚构数据，不代表真实员工或实际履约。

## 核心功能

- **需求与工单**：六字段解析、逐字段置信度、失败降级、SQLite 保存和工单状态管理。
- **人工协同**：低置信度审核、优先级建议与确认、处理建议的采纳／修改／拒绝。
- **多轮信息补全**：检查必需字段，只补原工单空字段，保护已有值和人工明确清空的字段。
- **人员与推荐**：技能资源池、规则评分、可选 AI 推荐解释；AI 不参与评分或派单决策。
- **确认派单**：核对信息与人员状态，阻止重复派单，同事务保存派单、人员占用和事件。
- **服务跟踪**：接单、开始、完成、异常、取消，禁止非法跳转，完成后按占用情况释放人员。
- **数据分析**：工单分布、最近 30 天趋势、补全与建议统计、派单与服务指标、运营日报。
- **面试演示**：一键执行十步、保存各步快照、导航回看、独立演示指标与操作记录。

## 系统架构

```text
客户自然语言需求
        ↓
AI解析（模拟／真实模型；失败保留原文并转人工审核）
        ↓
规则引擎（完整性、置信度、优先级、匹配与状态流转）
        ↓
运营工作台（补全、审核、方案评审、人工确认派单）
        ↓
服务执行（确认 → 接单 → 开始 → 完成／异常）
        ↓
SQLite 工单、人员、派单与事件 → 运营 Dashboard
```

```text
app.py                     页面入口：演示首页与运营工作台
pages/项目介绍.py          业务背景、架构、设计原则
modules/                   解析、规则、工单、补全、匹配、派单、服务与统计
modules/demo_view.py       完整演示的进度、结果与指标展示
modules/ai_client.py        优先级、建议、补全与推荐解释的调用封装
database/db.py             增量迁移、数据读写与事务
database/seed_demo_flow.py  复用业务接口编排十步演示，独立进程与独立数据库
database/seed.py            原有运营统计练习数据
database/seed_staff.py      原有虚构人员资源样例
tests/                     单元测试、事务与迁移测试、页面及业务验收

```

## Demo流程

在首页点击 **“一键运行完整演示”**。客户原文不包含姓名和电话，演示会明确显示补齐两项资料的过程。

| 步骤 | 展示内容 | 运营判断点 |
| --- | --- | --- |
| 1. AI解析需求 | 预置模拟的六字段结果与分数 | 区分已知信息与未提供信息 |
| 2. 生成工单 | 唯一工单编号、原文、人工审核状态 | 保留原始依据 |
| 3. 发现缺失信息 | 缺客户姓名、联系电话 | 信息不完整不能派单 |
| 4. 信息补全与审核 | 两轮回复补齐虚构姓名、电话，模拟审核 | 更新原工单，不重复建单 |
| 5. 确认高优先级 | 规则建议、演示运营最终确认 | 不因缺少电话降低优先级；年龄本身不等同高风险 |
| 6. 生成与采纳处理建议 | 待补项、步骤、注意事项及最终方案 | 建议需要运营评审 |
| 7. 推荐护理员 | 张护理员（演示）的评分、匹配理由和风险 | 登记可用不代表档期已核实 |
| 8. 确认派单 | 演示确认人、原因、派单编号，人员变忙碌 | 不由 AI 自动派单 |
| 9. 接单并开始服务 | 依次登记接单、开始时间 | 遵循服务状态机 |
| 10. 服务完成 | 完成记录、人员恢复可用、全过程事件 | 服务进度与工单人工状态独立保留 |

**五分钟讲解建议**：第一分钟讲业务背景与解析；第二分钟演示缺失检测、两轮补全；第三分钟说明人工分级与方案评审；第四分钟展示匹配、派单与服务状态；第五分钟回看事件和 Dashboard。

运行完成后，页面显示“已执行 10 / 10 步”。导航中的“当前讲解步骤”仅控制回看位置，不重新调用 AI 或重复执行业务动作。重复点击、刷新、重启后再次点击均复用已完成案例。

**隔离与真实性边界**：

- 完整演示保存在 `data/demo_flow/flow.db`，工作台仍使用 `data/autoflow.db`。完整演示不会写入工作台数据库或调用日志。
- 演示库的工单、人员、派单、对话、缺失字段、事件和结果快照均有 `is_demo=1` 标记；标记列仅添加到演示库，不修改真实库结构。
- 一键按钮通过独立子进程执行现有业务接口，避免临时切换主进程数据库路径影响其他会话。并发点击串行创建，失败不发布未完成的案例。
- 需求解析为本案例预置的六字段模拟输出；补全、建议与推荐解释使用现有规则路径。全部运营确认与服务操作均为演示模拟，不证明真实 AI 提取效果或实际履约效率。
- 工作台原有“一键演示”、批量工单和人员样例入口仍保留，属于写入工作台库的手动练习；与新的完整隔离演示入口不同。

## 技术实现

Python 3.12 + Streamlit + OpenAI SDK + SQLite；使用 python-dotenv、pandas、matplotlib，具体版本以 `requirements.txt` 为准。

- **解析接口**：`parse_customer_request(text)` 保持六字段结构：服务类型、预约时间、地址、客户姓名、电话、紧急程度，每项包含 `value` 和 `confidence`。真实模式使用 Structured Outputs，本地继续校验字段和分数；失败转人工审核。
- **置信度**：关键字段服务类型、地址、预约时间、电话低于 0.7 或缺失时需要审核。模型自评分和演示预设分数均不是经过验证的准确率。
- **优先级**：规则给建议、AI 可解释、运营确定最终等级；缺电话不降低优先级。原建议和最终等级分别保存。
- **规则匹配**：技能 40／20／0 分，区域 30／15／0 分，available 20 分、busy 5 分，基础 10 分；停用或技能不相关人员不进入候选。同分按人员编号排序。技能映射和区域规则集中在 `modules/matching_rules.py`；相邻区域未配置时不猜测。
- **状态与事务**：派单 `confirmed → accepted → in_service → completed`；接单或服务中可进入 `exception`；未结束记录可取消，异常不能直接完成。完成时仅释放没有其他未结束派单的忙碌人员，停用人员保持停用。业务写入与对应事件必须同事务。
- **数据迁移**：启动自动增量迁移，保留旧记录，不补造历史事件。业务表包括 `tickets`、`ticket_events`、`staff`、`staff_events`、`conversation_messages`、`ticket_missing_fields`、`dispatches`。
- **AI 调用隔离**：`parse`、`priority`、`advisor`、`conversation`、`recommendation` 分开记录；原需求解析成功率只计算真实解析尝试。日志包含任务、时点、耗时、模型、token 与安全错误描述。
- **统计口径**：工单完成率与派单完成服务数量分别计算；北京时间统计今日新增。平均接单／服务时长仅使用有效记录，没有数据时显示空值，不编造效率提升。
- **演示发布**：`demo_flow_snapshot` 仅存在于完整演示库，保存十步回看结果；主业务表及接口保持不变。演示时间是程序执行时点，不用于宣传服务时效。

## 运行方式

在项目根目录打开 PowerShell。已有 `.venv` 时跳过创建：

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m streamlit run app.py
```

保持 `config.py` 的 `DEMO_MODE=True`，无需密钥即可使用首页完整演示。切换“运营工作台”可逐项练习；侧边栏“项目介绍”用于面试讲解。

Linux 环境同样从项目根目录启动，不需要 Windows 盘符或本地已有数据库：

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m streamlit run app.py --server.address=0.0.0.0 --server.port=8501 --server.headless=true
```

应用启动自动创建工作台数据库；点击完整演示按钮才创建独立演示库。应用账号需要对 `data/`、`logs/` 有写权限，并允许启动同一 Python 解释器的子进程。平台使用其他端口时按其要求调整启动参数。

若要另行测试真实解析，在本地参考 `.env.example` 配置 `OPENAI_API_KEY`，可选 `OPENAI_MODEL`（代码默认 `gpt-4o-mini`），并将 `DEMO_MODE=False`。缺少密钥时回到演示模式。真实模式可能产生费用，应使用授权的测试数据；本阶段没有进行真实 API 联调。

完整演示按钮始终离线，即使工作台启用真实 AI 也不会调用付费模型。

运行全部测试：

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Phase 5A 新增 `tests/test_demo_flow.py`，覆盖完整案例、所有 demo 标记、真实数据与指标隔离、两轮补全、事件顺序、重复和并发点击、超时失败、页面导航及刷新。测试使用临时库，不修改本地业务数据。

本阶段验收结果：**471 个测试全部通过**（原有 455 个 + 新增 16 个），本地 Python 3.12.14 环境，全量运行耗时约 99 秒。

密钥、虚拟环境、SQLite 数据库、临时文件和日志由 `.gitignore` 排除。不要上传 `.env`、真实工单或客户原文日志。项目使用 [MIT License](LICENSE)。

## 项目亮点

- **以业务结果组织 AI 应用**：解析结果进入工单、运营确认、服务执行和数据分析。
- **人机职责明确**：AI 整理与解释，规则校验边界，运营承担最终确认。
- **可解释、可追溯**：保存原始需求、建议、人工决策及变化事件。
- **可验证的稳定性**：异常降级、事务回滚、历史迁移、并发保护与页面回归测试。
- **适合面试讲解**：独立 Demo 案例、十步导航、关键决策与运营指标，不需要阅读代码。

## 后续规划

本阶段只完成展示优化，未部署、提交 Git 或推送。

下一步建议先验收五分钟演示，再选择部署环境：

1. 面试用公开 Demo 可考虑 Streamlit Community Cloud，入口 `app.py`，使用 Python 3.12 和现有依赖，保持模拟模式、不上传业务数据。[官方部署说明](https://docs.streamlit.io/deploy/streamlit-community-cloud/deploy-your-app/deploy)
2. Community Cloud 不保证本地文件持久化，演示可以重新生成；真实工单需要可靠的持久存储和备份。[官方 SQLite 存储说明](https://docs.streamlit.io/develop/concepts/connections/connecting-to-data)
3. 部署验收再验证子进程运行权限、数据目录写权限、并发点击、重启后行为和完整演示；本地测试通过不代表云端已验证。
4. 后续真实 AI 联调使用独立测试数据评估字段提取和降级，不以演示分数或执行速度代替实测结果。

当前未提供登录、权限或租户隔离；本版本面向虚构数据演示。正式业务接入的访问控制、持久化和备份需另行规划，本阶段不扩展这些功能。

### 部署前检查与限制（Phase 5B-0）

- 发布源码时保留 `.env.example`、`data/.gitkeep`、`logs/.gitkeep`；不包含本地数据库、日志、虚拟环境、备份或真实 `.env`。Git 忽略规则不保护手动上传的整目录压缩包。
- Community Cloud 的入口填写 `app.py`，Python 选择 3.12，依赖使用根目录 `requirements.txt`。公开 Demo 保持 `DEMO_MODE=True`，不配置付费 API Key，也不上传真实客户或员工数据。
- 环境变量仅需 `OPENAI_API_KEY` 和可选 `OPENAI_MODEL`；模板中的 Key 为空。真实模式若使用平台 Secrets，应使用顶层同名变量，不放进额外分组；真实联调仍需单独验收。
- 当前工作台数据由所有访问者共享，访问者可以操作其中的工单；独立完整演示库也复用同一个虚构案例，不是用户级隔离。
- SQLite 事务与演示创建锁用于本地文件系统；AI JSON 日志使用进程内锁，不适合多个进程或多副本共同写入。此版本按单实例演示部署，不依赖网络共享文件锁。
- 异常退出可能留下被 Git 忽略的临时构建目录；正常成功、失败及重复点击已有清理与复用保护。损坏的演示库会报错并保留文件，不自动覆盖。
- 五项直接依赖均固定版本；已通过 Linux x86_64 / Python 3.12 的二进制依赖解析检查。间接依赖未全部锁定，云端实际启动、子进程权限与文件持久化仍需部署验收，不能以 Windows 测试代替。
