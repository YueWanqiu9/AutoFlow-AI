# AutoFlow AI

**AI驱动的服务运营自动化工作台**

将客户的一段自然语言需求，转化为可审核、可执行、可追踪的服务工单。

**V2.0 MVP · 471 tests passed · Python + Streamlit**

**五分钟了解项目**：阅读下方业务流程 → 本地启动 → 点击「一键运行完整演示」→ 回看运营决策与服务记录。完整 Demo 无需 API Key。

## 项目背景

在上门照护、保洁、康复辅助等服务场景中，运营人员需要把客户描述整理成明确的服务安排。这个过程常遇到五类问题：

- **客户需求非结构化**：服务内容、时间、地址混在一段话里，容易遗漏。
- **信息收集依赖人工**：缺少姓名、电话时，需要反复询问和录入。
- **工单处理顺序依赖经验**：优先级判断缺少可复核的依据。
- **派单效率低**：需要逐一核对服务人员的技能、区域和可用状态。
- **缺少过程数据沉淀**：处理原因、服务进度和异常情况难以回溯。

AutoFlow AI 围绕这些运营环节构建可演示的业务闭环，关注信息如何进入流程、决策如何确认、服务如何追踪。

## 项目介绍

本项目通过 AI 辅助运营人员完成 **需求理解、信息补全、优先级判断、处理建议、人员匹配、派单执行和运营分析**。

AI 将客户原文整理为结构化信息；规则检查完整性与业务条件；运营人员核对建议并作出最终决定。工单、派单及关键变更保存到 SQLite，Dashboard 展示运营数据。

例如，客户提出上门照护需求，却没有留下姓名和电话。系统识别缺失信息，围绕同一工单进行补问；运营确认优先级和处理方案后，再核对候选护理员并派单，最后登记服务进度。

## 核心业务流程

```text
客户需求输入
    ↓
AI需求解析
    ↓
信息补全
    ↓
人工审核
    ↓
优先级辅助判断
    ↓
AI处理建议
    ↓
人员匹配
    ↓
确认派单
    ↓
服务完成
    ↓
运营复盘
```

信息完整的工单无需补问；需要审核的工单必须先核对。派单后依次登记接单、开始和完成，异常由运营记录处理。以上是主流程，各环节通过明确操作触发。

## 核心功能

| 功能 | 当前实现 | 运营价值 |
| --- | --- | --- |
| 1. AI需求解析 | 提取服务类型、预约时间、地址、客户姓名、电话和紧急程度；真实模式使用 Structured Outputs，失败转人工审核 | 将原文整理为可核对的标准字段 |
| 2. 多轮信息补全 | 检测缺失项、生成补问、解析回复，更新原工单；保护已有值和人工明确清空的字段 | 保留沟通上下文，避免重复建单 |
| 3. AI优先级辅助 | 规则生成等级建议，AI 可辅助解释；运营确认最终等级并填写依据 | 使处理顺序有据可查；不是预测模型 |
| 4. AI处理建议 | 生成待补信息、处理步骤和注意事项，支持采纳、修改、拒绝；AI 不可用时降级为规则模板 | 将建议纳入人工评审流程 |
| 5. 服务人员管理 | 保存姓名、技能、服务区域和可用状态，记录人员变更 | 建立统一的服务资源池 |
| 6. 智能匹配推荐 | 规则按技能、区域和登记状态评分排序，AI 可解释匹配理由和风险 | 展示推荐依据，供运营核对档期与能力 |
| 7. 确认派单 | 运营填写确认人与原因；检查信息、审核状态及重复派单；后续登记接单、服务、完成或异常 | 把人员推荐落实为可追踪的执行记录 |
| 8. 完整Demo流程 | 一键执行十步模拟闭环，支持步骤回看、操作记录和独立演示指标 | 无需阅读代码即可理解业务过程 |

**过程追踪与复盘**：关键业务变更与操作事件同事务保存；Dashboard 提供工单、优先级、建议评审、补全、人员、派单及服务统计。工单人工状态与服务进度独立管理，避免混淆统计口径。

## 设计理念

**AI 辅助运营人员，最终确认权由人保留。**

| AI负责 | 运营人员负责 |
| --- | --- |
| 信息整理：理解需求、提取字段 | 核对原文、补齐信息、审核结果 |
| 判断辅助：解释规则依据、提示风险 | 确认优先级、处理异常 |
| 提供建议：整理处理步骤与注意事项 | 决定最终方案、确认派单与业务决策 |

规则约束业务边界：信息不完整不能直接派单，推荐不等于人员一定有档期，工单状态与服务进度不能随意跳转。AI 调用失败时保留规则或人工处理路径，不阻断需求保存。

模型自评分和 Demo 预设分数均不代表经过验证的准确率；项目不宣称已实现实际运营效率提升。

演示按顺序执行：**模拟解析 → 创建工单 → 发现缺失 → 两轮补全并审核 → 确认高优先级 → 生成并采纳建议 → 推荐护理员 → 确认派单 → 接单并开始 → 服务完成**。

| 讲解时间 | 建议展示 | 重点 |
| --- | --- | --- |
| 第1分钟 | 客户原文与解析字段 | 自然语言如何进入业务流程 |
| 第2分钟 | 缺姓名、电话与两轮补问 | 更新原工单，保护人工确认信息 |
| 第3分钟 | 优先级与处理建议 | 规则依据和人工最终确认 |
| 第4分钟 | 人员推荐、派单与服务流转 | 推荐如何成为执行记录 |
| 第5分钟 | 操作历史与 Dashboard | 决策可追溯，过程可复盘 |

**演示边界与数据标记：**

- 完整演示中的客户、人员、联系方式和服务结果均为虚构，相关数据库记录统一标记 `is_demo=1`。
- 完整演示使用独立库 `data/demo_flow/flow.db`，不写入工作台库 `data/autoflow.db`，不影响工作台统计或 AI 调用日志。
- 解析使用预置模拟结果，补全、建议与推荐解释使用现有规则路径；客户回复、运营确认和服务执行均为模拟操作。完整演示不调用付费 AI，也不代表真实 AI 联调结果。
- 十步执行完成后，导航仅用于回看。重复点击和刷新不重复创建案例；已有完整演示库时重启后仍可复用。
- 原有工作台「一键演示」和样例加载属于写入工作台库的手动练习，也有演示提示；不要与完整隔离演示入口混淆。
- 公开工作台没有用户隔离，访问者可以查看和修改共享数据。仅限使用虚构示例，禁止输入真实姓名、电话、地址、身份证号或 API Key。页面提示不提供敏感信息自动识别、过滤或访问控制。

## 项目限制

- **个人作品 Demo，非生产环境**：使用模拟业务数据，尚未进行真实业务规模与实际履约效果验证。
- **SQLite 仅用于演示，不作为本项目的生产存储**：需要可写目录；云端本地文件不保证持久保留。文件丢失后可以重新生成模拟案例，不能恢复此前手动录入的数据。
- **未设计多租户权限**：无登录和访问控制，工作台由访问者共享；公开 Demo 不应放入真实客户信息或付费 API Key。
- **面向单实例**：AI 日志采用进程内锁，不支持多个进程共同写入；未提供复杂调度、实时排班、GPS 或支付。
- **模拟不等于实测**：预设置信度不是准确率，演示执行时间不是实际服务耗时，登记可用不保证人员档期可用。
- **云端仍待验收**：Linux 依赖解析检查已通过，但子进程权限、目录写入、实际启动和重启后的行为仍需实测。

## 本地运行

需要 **Python 3.12**。在项目根目录打开终端，已有虚拟环境时跳过创建步骤。

**Windows / PowerShell：**

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m streamlit run app.py
```

**Linux：**

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m streamlit run app.py
```

保持 `config.py` 中 `DEMO_MODE=True`，即可在浏览器中运行完整演示，无需 API Key。应用自动初始化数据库，不依赖本地已有工单；需要对 `data/`、`logs/` 有写权限，并允许启动 Python 子进程。

| 配置项 | 值 |
| --- | --- |

| Python | `3.12` |
| Dependencies | 根目录的 `requirements.txt` |

配置方式见 [Streamlit 官方部署说明](https://docs.streamlit.io/deploy/streamlit-community-cloud/deploy-your-app/deploy)。后续推送到部署分支的改动会触发应用更新，应先完成本地审核和测试。
